# Generation Job Publication Contract

This document defines the canonical publication contract for the uniform
generation surface introduced by #104 (spec #102, ADR-0014, DEC-003/004) and
extended by #105 (References). Dependent tickets (#105, #107, #108, #109)
consume and adhere to this contract — no dependent delivery guesses a private
schema.

The uniform operation is one prompt-only source-image Generation Job: a caller
prompt, an output intent (full-canvas or isolated — a request parameter, not a
subject category), caller-selected sizing, and a count. Ply adds no subject
policy: no text/logo ban, no mandatory identity Reference, no approval gate
(ADR-0014). Matting is not part of this operation (ADR-0015) — generation does
not require Matting weights, and isolated intent is never reported as verified
alpha.

## 1. Directory layout

Generation Job records live under `out/generation/` (overridable by the CLI's
injected root; the default is `<cwd>/out/generation`):

```
out/generation/<jobId>/
├── job.json                 # the record (schema below) — the commit point
└── outputs/                 # content-addressed generated bytes (sha-256)
    └── <sha256>.<ext>
```

Job ids match `^[a-z0-9][a-z0-9-]*$`; the auto id is `gen-<yyyymmdd>-<8 hex>`.
Creating over an existing job id (`job.json` present) is refused — a new
request records a new Job; nothing is ever overwritten.

**Relationship to the legacy `out/jobs/` surface.** The legacy Plate/Object/
Creator records (schemaVersions 1–5) are deliberately NOT reused: their
`recordRun` is welded to the (kind, MatteEngine) contract — every non-plate
legacy kind requires the matting pass, and their request shapes carry
category-specific policy. The uniform surface has its own record and root so
the legacy lifecycle is untouched until its separately owned retirement
(#114/#115). `out/generation` records are the single authoritative home for
uniform Generation Job facts; dependent tickets must not duplicate request
facts elsewhere.

## 2. Record schema (schemaVersion 1, kind "generation")

```json
{
  "schemaVersion": 1,
  "jobId": "gen-20260908-ab12cd34",
  "kind": "generation",
  "createdAt": "2026-09-08T12:00:00.000Z",
  "request": {
    "prompt": "the caller's prompt, trimmed at the ingestion boundary",
    "intent": "full-canvas | isolated",
    "model": "registry key or raw gateway id, as the caller wrote it",
    "sizing": { "kind": "size", "width": 1080, "height": 1080 }
            | { "kind": "aspectRatio", "ratio": "4:5" },
    "count": 1,
    "temperature": 0.7
  },
  "run": {
    "ranAt": "2026-09-08T12:00:05.000Z",
    "model": "resolved provider id actually called",
    "fullPrompt": "the effective text sent to the model",
    "costUsd": 0.0045,
    "costMeasured": true,
    "warnings": ["..."],
    "outputs": [
      { "contentHash": "<sha-256>", "file": "outputs/<sha-256>.png", "mediaType": "image/png" }
    ]
  }
}
```

Facts and their one home:

- **The record is the single authoritative home for the request facts**
  (prompt, intent, sizing, model selection, count, temperature) and for the
  run facts (resolved model, effective prompt, outputs, warnings, cost). The
  published record is what `generate show` returns verbatim; dependent
  tickets read it, never a second copy.
- **Outputs are content-addressed** by sha-256 of the exact bytes on disk;
  `contentHash` is verifiable against the file at any time.
- **`run.fullPrompt` is the effective request provenance**: the caller's
  prompt verbatim, plus (isolated intent only) the fixed isolation-format
  line, plus (aspect-shaped models only) the `Output aspect ratio: W:H.` line.
  Nothing else is added — no zone guidance, no subject bans, no identity
  recipe (ADR-0014). Isolated intent's framing line requests margins, a plain
  uniform background, and crisp edges; it never requests transparency, a
  painted checkerboard, or true alpha (ADR-0015).

## 3. Request validation (one ingestion boundary)

`validateUniformRequest` (src/generation.ts) is the single ingestion point.
Semantic validation happens there, before any provider call — a refused
request costs nothing:

- Non-empty prompt; intent is `full-canvas` or `isolated`; count 1–8.
- Model resolution via the shared model registry (`src/models.ts`): registry
  keys or raw gateway ids; unknown names are refused with the options.
- Sizing must match the model's provider call shape — `--size WxH` for models
  whose provider call takes explicit size, `--aspect W:H` for the rest. A
  mismatch is refused by name before any spend. Omitted sizing fills the
  **model-neutral default: 1024x1024 / 1:1** — no platform geometry is ever
  defaulted. Caller-selected sizes pass through as given; whether a provider
  accepts a particular size/ratio is the provider's own explicit validation.
- `--temperature` is multimodal-only.

The CLI layer additionally classifies pure syntax problems as usage errors
(exit 2); domain refusals exit 1 with an actionable message.

## 4. Provider seam

`UniformProvider` (src/generation.ts) is the seam the outbound request is
captured at: `image({ model, prompt, size?, aspectRatio? })` for size/aspect
image models, `text({ model, prompt, temperature? })` for multimodal models.
Image-kind requests are built through `buildImageRequestArgs` (src/generate.ts)
— the one home of the image-kind provider request shape — so the uniform
surface cannot drift from the legacy call shape. Legacy callers pass no
explicit sizing and keep their exact request bytes (proven by
test/image-request-args.test.ts). `#105` extends these shapes with References;
the record's `request` grows accordingly.

Missing-image responses are refused by name; provider errors surface verbatim.

## 5. Publication discipline and failure boundary

- Outputs are persisted first; `job.json` is the commit point, written last.
  There is no moment where a record exists without its outputs.
- A caught failure (provider error, missing image, write failure, refusal)
  removes the freshly created job directory and reports `{ok: false}` with a
  nonzero exit — nothing is left that reports success. A stale directory
  without `job.json` (a hard crash) may be reclaimed by a retry of the same
  id; the record never existed, so no lineage is destroyed.
- No command on this surface reads or writes Project state (`ply.json`,
  `compositions/`, `layers/`, `content/`, `renders/`). Ingestion into
  Projects is #107's work and goes through the normal Layer contracts.

## 6. Matting boundary

This surface never imports the Matting engine and never runs a matting pass:
generation works without Matting weights (US-002, ADR-0015), the engine-call
tripwire test (`test/generation.test.ts`) fails on any accidental import, and
isolated-intent runs carry the recorded warning that intent is a generation
request, not a matte. The independent matting operation is #106's ownership.

## 7. Command contract (US-005)

- `ply generate <prompt> [options]`, `ply generate show <jobId>`,
  `ply generate list` — see the module help for the full syntax.
- Default output is compact human text; `--json` emits `{ok: true, jobId,
  jobDir, job}` / `{ok: false, error}`. Exit codes: 0 ok, 1 failure, 2 usage.
- `show` and `list` are pure local reads: they never invoke generation and
  work offline. Richer evidence presentation (review sheets, candidate
  comparison) is #109's ownership.
- `--json` payloads carry the full published record, so an agent inspects the
  effective request, outputs, and provenance without a second read.
