# Handoff — thumbnail full-pipeline run from scratch (2026-09-10)

First end-to-end pass over the **shipped spec #132 surface with live
generation**: two fresh nano-2 Generation Jobs (tool default, no `--model`)
→ local BiRefNet matte → Project ingestion with retained provenance →
in-tool resize/anchor/shadow/outline → local render + byte-identical replay.
Unlike v2 (which re-ingested v1's retained records for $0), every pixel here
is new. Total billed spend: **$0.134** (2 × $0.067 nano-2, `costMeasured`).

## What this run proves beyond v2

- **The default path works end-to-end.** Both generations omitted `--model`
  and landed on `google/gemini-3.1-flash-image` outbound, retained as
  `request.model: nano-2` in provenance (#141 holds on the live path, not
  just the injected seam).
- **Nano-2 background is a different artifact than GPT's.** 1376×768 native
  (not 1280×720), pixel-art-leaning style vs v1's smooth cartoon. Same
  prompt, different model → different image. Callers who need exact canvas
  pixels from the provider should pass `--model gpt-image --size 1280x720`
  explicitly; the default trades exactness for the reviewed quality/cost
  preference. The 1376→1280 crop here cost nothing in quality.
- **No refusal on the cartoon prompt.** The v1 F5 refusal was the explicit
  "Luigi/L-emblem" wording on gpt-image; the genericized hero wording
  succeeds on nano-2 first try, both then and now.
- **Full lineage closes the loop v1 left open.** `layer inspect` on Luigi
  traces matte `v3-luigi` → Generation Job `v3-char` by content identity;
  the 1024 source bytes are retained and the 450 size is placement-only.
  F1/F9 stay fixed with newly generated bytes, not just retained ones.
- **One render total.** Measure → anchor → effects → re-anchor → render.
  The v2 ordering lesson applied cleanly on unfamiliar pixels.

## Model sizing capabilities (caller decision)

The two generations in this run make the per-model contract concrete, so it
is recorded here rather than left as tribal knowledge. One registry
(`src/models.ts`) owns it; the CLI refuses mismatches before any spend.

| Model | Key | Sizing flag | Default | Exact pixels? |
| --- | --- | --- | --- | --- |
| GPT Image 2 | `gpt-image` | `--size WxH` only | 1024×1024 | Yes — the provider returns what was asked (v1 bg: exactly 1280×720) |
| Nano Banana 2 Lite / 2 / Pro | `nano-lite` / `nano-2` / `nano-pro` | `--aspect W:H` only | 1:1 | No — the provider picks dimensions for the ratio (this run: 16:9 → 1376×768) |
| FLUX.2 Flex, Seedream, Recraft | `flux` / `seedream` / `recraft` | `--aspect W:H` only | 1:1 | No — same ratio contract |
| Raw gateway id | e.g. `bytedance/...` | `openai/*` → `--size`, everything else → `--aspect` | per shape | Provider-dependent, no capability claim until qualified |

Related one-home rules in the same registry: `--quality low|medium|high`
is GPT Image 2 only; `--temperature` is multimodal (Gemini) only;
References are refused on `flux`/`recraft`/raw ids before any spend.

The caller decides per job, and both routes are first-class:

- **Ratio + fit locally** (this run's bg): generate with the default
  model at the nearest ratio, then center-crop via placement (no
  resampling) or `--resize-to` (resamples, placement-only, source
  retained). Best when the reviewed default model is wanted and a few
  edge pixels don't matter.
- **Exact pixels from the provider**: pass
  `--model gpt-image --size 1280x720` explicitly. Best when the canvas
  must be filled edge-to-edge with no crop step. Costs less ($0.0045
  measured text-only) but is a different image for the same prompt —
  model choice is a look choice, not just a size choice.

## New observations

1. **Nano-2 ignores exact pixels; it takes ratios.** `--aspect 16:9`
   returned 1376×768. Any caller promising exact output dimensions must
   either pick a size-taking model (`gpt-image` + `--size`) or plan a
   cover-crop/resize step — worth one line in the operating skill.
2. **Matte wall time ~6 min still** (11:35 → 11:41), unchanged from the v1
   F6 datapoint. Quantified again for #130; no design claimed.
3. **Replay writes a sibling manifest into `renders/`.** Pruned after the
   `cmp` check to keep the example at one render + one manifest (same
   hygiene note as v2).
4. **Matting artifact in white glove interiors** — promoted to its own
   section below (spec input).

## Matting finding — interior transparency in white regions (spec input)

### What was observed

In all three renders (v1, v2, v3), parts of Luigi's white gloves render
with the background sky showing through them. Zoom crops of source →
matte-on-magenta → final render (scratch, since removed) confirm the matte
is the cause, not the composite:

- Raised fist interior: fully transparent at the center (sampled RGBA
  255,255,255,**2**).
- Lower glove interior: semi-transparent wash (center alpha **185**,
  ~27% background bleed).
- A control sample on the cheek is fully opaque (alpha 255) — the defect
  is specific to near-white interiors, not a global alpha failure.
- Flood-fill from the image border over the transparent mask counts
  ~1,980 fully-transparent *interior* (border-unreachable) px in the v3
  matte (bbox x584–660, y158–276, inside the raised fist) and ~2,264 px
  in the v1 matte: systematic across versions and across newly generated
  bytes, not a one-run flake. The semi-transparent wash is additional
  (part of ~27k sub-opaque px inside the subject bbox, edges excluded).

### Is matting different from segmentation? Yes, and Ply does the latter

- **Segmentation** answers per pixel "subject or background?" — every
  pixel is judged independently, interiors included.
- **True matting** takes a trimap (known foreground / known background /
  narrow unknown band around edges) and solves alpha *only inside the
  unknown band* — interiors are never questioned, so a white glove
  interior cannot become transparent by construction.
- Ply's `ply matte` is segmentation-as-matte: BiRefNet HR predicts a
  foreground-probability mask locally (`src/segment.ts`), and
  `composeMatte` (`src/matte.ts`) writes mask brightness directly as the
  alpha channel with RGB untouched. There is no trimap, no topology
  enforcement, and no hole-filling anywhere in the pass (verified by code
  inspection). The true-alpha gate (`src/alpha.ts`) only checks ≥1%
  transparent *and* ≥1% opaque, which a holed matte passes trivially.

### Why white-on-white fails

The isolated-intent contract asks the provider for a plain uniform — in
practice white — background, and the hero's gloves are textureless
near-white. With no interior texture to key on, those pixels score low
subject-probability and are read as background. The generation prompt and
the segmenter are working against each other: the background color the
prompt is told to request is the color most likely to erase white subject
parts.

### Is the desired goal possible with the current implementation?

Cut the silhouette without touching interior pixels: **not with the
current pass as-is** — a direct mask-to-alpha write cannot promise it.
Only alpha is wrong (colors are never modified), so every remedy is
alpha-only. Candidate directions, smallest first, for the spec to weigh:

- (a) **Flood-from-border hole fill**: force border-unreachable
  transparent px to opaque. Fixes the ~2k full punch-throughs; does
  nothing for the semi-transparent wash; near-zero risk to real detail.
- (b) **Largest-connected-component + hole fill**: the standard remedy
  for exactly this class — keeps the dominant subject mass, fills its
  enclosed holes. Fixes holes robustly; still leaves partial-alpha
  interiors washed.
- (c) **Prompt-side mitigation**: request a mid-tone (e.g. neutral gray)
  uniform background for isolated intent instead of white, ending
  white-on-white confusion at the source. Caller-visible contract change
  to the generation framing line; helps whites but mirrors the failure
  onto mid-tone subjects.
- (d) **Trimap-based matting** (e.g. ViTMatte over an auto-trimap derived
  from the dilated/eroded mask): real matting, interiors protected by
  construction, soft edges preserved. Largest work — new weights,
  new pass, new qualification.
- (e) **Interior alpha floor / threshold**: clamping sub-opaque interior
  px risks destroying legitimate soft detail (motion blur, thin fabric)
  with no principled boundary — not recommended without (b) or (d).

Not fixed in this run; recorded here as evidence for the next spec.

## Further test notes (small, verified)

- **Placement numbers don't transfer across generations.** Identical
  Luigi placement and scale — (70, −22) at 450 effective — yields painted
  (183, 29) 235×348 in v1/v2 but (165, 22) 260×362 in v3: the new hero
  fills its frame differently. Re-measure after every ingest; never copy
  placement between assets, even for "the same" subject.
- **The bg crop was hand arithmetic the tool could have done.** I placed
  (−48, −24) from (1280−1376)/2, (720−768)/2 by hand; `--anchor
  center,center --x 640 --y 360` resolves to exactly the same placement
  in one shot (painted == content for an opaque bg). Prefer anchors over
  arithmetic — a skill-guidance candidate.
- **Text measurement is exactly deterministic across projects.** The v2
  and v3 banners (same spec, independent projects) measure identically —
  box (474, 41), painted (432, 36) 416×185 — and the retained Anton bytes
  hash identically (`3de40176…` in both `content/` stores). Content
  addressing and renderer-consistent measurement doing their jobs.
- **Returned ratios are approximate, not exact.** 16:9 came back 1376×768
  (1.792, ~0.8% off 16:9) — a second reason, beyond unknown dimensions,
  that ratio-model callers must fit locally rather than assume geometry.
- **Verification replays pollute render history.** `replay --out /tmp/…`
  still writes a manifest into the Project's `renders/` (bare
  `<id>.manifest.json`, no composition prefix), so every byte-identity
  check needs a prune step afterward. Real behavior, not a bug claim —
  but example hygiene (and any replayer) must account for it.
- **Engine fallback leaves no record trace.** The matte run's stderr
  showed partial CPU fallback for unassigned nodes, yet the matte record
  carries `warnings: []` — the fallback never throws, so the seam that
  records warnings never sees it. A reader of the record alone cannot
  tell the run partially fell back; relevant to #130's latency reading.
